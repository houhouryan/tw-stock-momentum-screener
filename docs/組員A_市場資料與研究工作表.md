# 組員 A 工作表：市場資料與研究負責人

## 1. 角色定位

**核心任務：**確保系統使用的市場資料、訊號、標籤、成交規則與研究結論在台股情境下正確、可解釋、可驗證。

組員 A 不是只負責提出選股想法或撰寫報告，而是「金融領域程式模組的主要開發者」。所有市場規則都必須落成程式、測試資料與驗收證據，不接受只存在於口頭、Excel 或簡報中的定義。

對應文件：

- [系統 SDD v0.2](./台股飆股候選偵測與續航評估系統_SDD_v0_2.md)
- [組員 B 工作表](./組員B_系統實驗與模型工作表.md)

## 2. 成功標準

組員 A 的工作完成，不是指「找到看起來會漲的股票」，而是同時符合：

1. 任一資料欄位都能說明來源、單位、發布時點、缺值意義與修訂方式。
2. Universe、Signal、Label 與成交模擬都有明確公式及邊界測試。
3. 除權息、減資、停牌、下市、漲跌停等案例不會使報酬或成交結果失真。
4. 研究結果能區分模型排名、產品展示及交易績效，不混用指標。
5. 所有結論能由固定資料版本、設定與程式重新產生。
6. 能在口試時獨立解釋從 Raw 資料到 Label、回測結果的完整金融邏輯。

## 3. 主要責任與程式範圍

### 3.1 主要負責

- 官方與第三方資料來源盤點、來源條款確認及欄位語意。
- TWSE／TPEx 股票基本資料、交易日曆、日價量、法人、融資融券、公司行動與市場指數。
- 資料正規化中的市場代號、單位、價格、股數及日期規則。
- 每日標的池 Universe。
- V01、P01、P02、P05、R01、C01、C02 訊號。
- DEF-RANK、DEF-CONTINUATION、DEF-SURGE 標籤。
- T+1 成交、T+10 出場、no-fill、成本、停牌與下市處理。
- 主題定義、成分證據、公告事件方向及人工標註。
- 資料字典、來源登錄、研究方法、結果解釋與限制。

建議主要維護的程式路徑：

~~~text

src/hotstock/data/normalize.py
src/hotstock/data/quality.py
src/hotstock/research/universe.py
src/hotstock/research/labels.py
src/hotstock/signals/
src/hotstock/backtest/fills.py
src/hotstock/backtest/portfolio.py
tests/fixtures/
tests/unit/test_universe.py
tests/unit/test_signals_*.py
tests/unit/test_labels.py
tests/unit/test_fills.py
docs/data_dictionary.md
docs/source_registry.md
~~~

### 3.2 必須共同簽核

以下項目由組員 B 實作或共同實作，但組員 A 必須審查：

- PIT 時間規則是否符合資料實際發布方式。
- 資料庫欄位是否保留足夠的金融語意與修訂資訊。
- 百分位、A／B／B+ 排名是否正確使用共同 Gate 集合。
- 回測成本、成交時點及績效報表是否沒有誤導性。
- Candidate 證據卡是否能忠實解釋股票入選原因。
- 主題與公告 LLM 的 Gold set 是否具備金融判讀品質。

### 3.3 非主要責任

- Flask、HTMX 畫面框架。
- systemd、Gunicorn、SQLite migration framework。
- LLM 呼叫框架與結構化輸出驗證器。

組員 A 仍須理解上述模組的輸入與輸出，並能協助故障驗收。

## 5. 固定交接介面

### A 交給 B

| 交付 | 格式 | B 可以依賴的保證 |
|---|---|---|
| 資料欄位定義 | data_dictionary + typed schema | 單位、Null、自然鍵及可用時間已明定 |
| Raw fixture | 原始檔 + request metadata + hash | 可離線重播，不需當場連網 |
| UniverseResult | 純函式輸出 | 每個納入／排除都有原因 |
| SignalResult | triggered、strength、available、evidence | 不讀 Label，不自行查目前日期 |
| LabelFrame | label、status、NaN reason、path summary | 未成熟與不可用不會填 0 |
| Trade fixture | 進出場、成本、公司行動、預期結果 | 可用於回歸測試 |
| 主題／公告標註 | versioned JSON／CSV | 保留原始標註、仲裁與 evidence |

### A 需要 B 提供

- 可安裝且能跑測試的專案骨架。
- SourceAdapter、repository 與純函式介面。
- PIT view、run manifest、config hash 及 immutable run。
- 可鎖住 validation／holdout 的研究環境。
- 每日 quality、candidate、scorecard 與回測報告。
- 可重現的測試、CI 與開發指令。

## 7. 個人 Definition of Done

一項工作只有符合下列條件才可標示完成：

- 程式、測試與文件同時更新。
- 使用 fixture 可離線重現。
- 正常、缺值與至少一個金融邊界案例通過。
- 沒有直接讀取未來資料或系統目前日期。
- 所有排除、降級與 unavailable 都有原因碼。
- 組員 B 已完成 review，或雙方已在 ADR 簽核。
- 能用三分鐘向非開發者解釋輸入、處理、輸出與限制。

## 8. 評量指標

不以「推薦股票漲多少」作為個人績效。組員 A 應以以下證據評量：

- 資料來源與資料字典的完整度。
- Universe／Signal／Label／成交測試通過率。
- 特殊市場案例覆蓋數與人工驗算一致率。
- 資料品質問題的發現與可追溯處理紀錄。
- 研究協定是否在指定日期凍結。
- 結果報告是否包含負面結果與限制。
- 自己主要負責的程式碼、測試、文件與 PR 紀錄。

## 9. 口試主要負責回答

- 為什麼 Universe 使用 120 日、10 元及 20 日均額門檻。
- 各訊號的市場意義、窗口與缺值處理。
- 為什麼 Gate 與排名要分開。
- 如何處理除權息、減資、停牌、下市與漲停無法成交。
- DEF-RANK、續航、飆股標籤的差別。
- 為什麼歷史 B+ 只能稱 retrospective。
- 回測結果為何不等於實際可交易報酬。
- 系統為何不是投資建議或自動交易工具。
