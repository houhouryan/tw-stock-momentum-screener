## 1. 結論先行

工作報告 001 對現況、風險與未驗證事項交代得相當完整，可以作為有效的規劃紀錄；但原 B0 計畫把多個高風險工作合併成一天，並準備一次凍結過多 Domain model、一次建立 23 張資料表。若照原日程執行，很可能到一天結束才發現基礎介面或 Schema 方向錯誤，返工會同時影響 A、B 兩人。

本次審查將 B0 改成 14 個短輪次。每輪只交付一個可以獨立驗證的能力，完成後必須：

1. 新增一份組員 B 工作報告。
2. 停止後續開發。
3. 等待新的檢查報告明確標記 PASS。
4. 未取得 PASS 前，不得因為「還有時間」而先做下一輪。

本報告是 B0 的執行指令與修改指南。舊的 B0 v1 保留作歷史規劃，不覆寫、不刪除，但不再作為執行順序依據。

## 4. 發現與修改指南

### B0-F01｜Blocker｜新計畫仍被舊新聞工具污染

**證據**

- README 仍把舊新聞工具列為可運行元件，包含執行指令、遷移計畫及「先跑著」的主張。
- B0 v1 的 runtime dependencies 包含 feedparser。
- B0 v1 的 D-02 與風險分析仍把新聞不中斷視為 B0 考量。

**影響**

這與 DEC-002 的「完全不納入新主線」直接衝突，也會讓工程師浪費時間處理無關依賴、Schema 與相容性。

**修改指南**

1. 新 pyproject.toml 不得加入 feedparser 或任何只服務舊新聞工具的依賴。
2. 新 src/hotstock/ 不得 import 舊 src/db.py、src/sources.py、src/pipeline.py 或 run_news.py。
3. README 移除舊新聞執行方式、遷移承諾與每日維運說明；只保留新系統現況與新架構。
4. 不刪除舊檔案；它們保持未接線狀態，直到專案經理另行授權。
5. 測試與品質命令只掃描新 package、正式 tests 與必要 scripts，不為舊工具補錯。

**驗收**

- 新依賴無 feedparser。
- 新 package 搜尋不到對舊新聞模組的 import。
- README 不再指示使用者執行 run_news.py。

### B0-F02｜Major｜原計畫單輪範圍過大，沒有強制停點

**證據**

- 原日程準備一天完成大部分 Domain contract 與 Adapter。
- 原日程準備一天完成 15 張業務表。
- 原計畫只要求每日更新狀態，沒有「審查通過前不得繼續」的控制。

**影響**

介面或 Schema 一旦錯誤，A 可能已基於錯誤契約同步開發，返工會成倍放大。

**修改指南**

- 改用本報告 §6～§20 的 14 個短輪次。
- 每輪上限約 2～4 小時；超過上限不准自行擴張範圍。
- 完成一輪後立即新增工作報告並停下。
- 下一輪是否解鎖只以後續檢查報告的 PASS 為準。

**驗收**

- 工作報告一次只對應一個 B0-Rxx。
- 報告最後明寫「下一輪尚未開始」。
- Git diff 不含下一輪檔案。

### B0-F03｜Major｜23 表初始 migration 過度前置

**證據**

原計畫在 B0-05 一次納入 feature、label、candidate、scorecard、theme 等尚未被 B0 消費的表。

**影響**

這些表的實際契約仍會隨 Label、Score、Theme 與產品切片驗證，過早建立只會讓後續 migration 更難，而不是更穩。

**修改指南**

B0 只建立以下 11 表：

1. schema_migration
2. source_registry
3. license_snapshot
4. source_artifact
5. pipeline_run
6. run_input_artifact
7. active_run
8. security_master_scd
9. trading_calendar
10. daily_price
11. market_index

其餘表不得先放空殼。每張表在首個消費它的 Slice 以新 migration 加入，禁止修改已套用 migration 的內容。

**驗收**

- B0 migration 只含上述 11 張業務／控制表。
- migration 有順序、checksum 與 schema_migration 紀錄。
- 已套用 migration 被改動時啟動必須失敗，而不是用 IF NOT EXISTS 靜默略過。

### B0-F04｜Major｜Domain contract 過早包含下游完整物件

**證據**

原 B0-03 同時規劃完整 ThemeFrame、ScoreResult、TradeResult、40 多欄 CandidateCard。

**影響**

尚未走過單日切片就凍結產品、回測與主題契約，容易把推測當需求，並增加 A、B 同時返工的範圍。

**修改指南**

B0 僅完成：

- 共用 enum 與 error。
- PitMetadata。
- FetchRequest、RawArtifact、NormalizedBatch、SourceHealth。
- PipelineRun 的基礎模型。
- UniverseResult、SignalResult、SignalFrame。
- LabelFrame 的最小跨組介面。

ThemeFrame、ScoreResult、TradeResult、CandidateCard 由使用它們的後續輪次定義。不得在 B0 建立「先放著」的完整 model。

**驗收**

- B0 domain 目錄沒有未被本階段或 A1 使用的產品／回測完整物件。
- 每個 model 都有至少一個 consumer 或明確的 A-facing contract。

### B0-F05｜Major｜README 與文件基線已過期

**證據**

- README 仍聲稱 repo 只有計畫書 v2.6.1。
- README 的分工衝突說明未反映專案經理已核准的新分工。
- README 大量保留舊新聞操作內容。

**修改指南**

第一個輪次先完成文件基線校正：

- 文件表改列計畫書 v2.6.2。
- 明確寫 SDD v0.2 > 有效 ADR > 工作表 > 計畫書背景；若 SDD 與計畫書衝突，以 SDD 為準。
- 明確寫新工作表取代計畫書 §17。
- 移除舊新聞操作內容。
- 將本檢查報告列為目前 B0 執行清單。

**驗收**

- 新加入的工程師只讀 README，不會被引導去執行或遷移舊新聞工具。
- README 不再寫「v2.6.2 缺漏」。

### B0-F06｜Major｜原計畫允許「無意見即視為採用」

**證據**

B0 v1 §5 對部分技術選型寫「若無意見即視為採用」。

**影響**

這違反專案經理指定的決策流程。沉默不是核准，任何會改變專案範圍或契約的選擇都不能自行通過。

**修改指南**

- 已列於 DEC-001～DEC-012 的事項可直接執行。
- 未列入的重大選擇一律停止該輪、寫入工作報告，不得套用預設值。
- 純局部、可逆且不改公開契約的實作細節可以提出方案，但仍須在工作報告說明。

**驗收**

- 後續計畫與工作報告不再出現「未反對視為同意」。

### B0-F07｜Minor｜工作報告缺少版本定位

**證據**

工作報告列出檔案動作，但沒有 base commit、head commit、實際 diff 範圍；同時 Git 中存在 README 提交，無法只從報告判定該輪與提交的對應。

**修改指南**

未來每份工作報告新增：

- 開始時 branch 與 base commit。
- 結束時 head commit；尚未 commit 就明寫 uncommitted。
- git status --short。
- git diff --stat 或本輪 commit 的 stat。
- 明確區分「本輪修改」、「本輪前已存在」、「他人同時修改」。

**驗收**

審查者不需猜測，即可把報告中的交付物對應到確切 diff。

## 5. 強制執行規則

### 5.1 一輪一停

1. 只執行目前被解鎖的輪次。
2. 勾選該輪清單並保存驗證輸出。
3. 在 docs/工作報告/ 新增一份工作報告。
4. 停止工作，不開始下一輪。
5. 等待 docs/reviews/member-b/ 中新的檢查報告。
6. 只有檢查結論為 PASS，且明確寫出下一輪 ID，才能繼續。

即使本輪提早完成，也不得順手建立下一輪檔案。

### 5.2 Checklist 使用方式

- 不修改本檢查報告。
- 將當輪 checklist 原樣複製到工作報告，再以 [x]／[ ] 標記。
- 未完成項目保留 [ ] 並解釋原因，不得刪除。
- 額外完成的工作列為範圍外變更；範圍外變更可能導致整輪退回。

### 5.3 遇到決策或阻塞

- 立即停止，不自行採用預設方案。
- 寫工作報告，狀態標為 BLOCKED。
- 說明背景、選項、影響與建議。
- 不開始下一輪。
- 審查者會暫停檢查並直接請專案經理決定。
