### 3.2 為什麼先寫測試再改實作

checklist 5 要求記錄「舊實作上確實失敗」的紅燈證據。若先改實作再補測試，就無法證明測試真的抓得到那個缺陷，測試也可能只是照著新實作寫出來的同義反覆。因此 P5 只動測試檔、完全不碰 `fixture.py`，跑出紅燈並記錄實際輸出後，才進入 P6。

P9 的既有測試修正刻意排在實作之後：那些測試在舊契約下是對的，是新契約讓它們失效，所以要等新契約成立後再依實際失敗情況修正，並分開陳述兩批紅燈的性質。

### 3.3 lineage guard 的驗證順序

依審查報告 §5.3 固定為：

```text
1. 傳入物件是 RawArtifact                  -> CONFIG_INVALID
2. source 與 dataset 等於 adapter           -> CONFIG_INVALID
3. artifact.request 完整等於 fixed request  -> CONFIG_INVALID
4. content_hash 等於本次讀到的 raw bytes    -> DATA_QUALITY
5. 8 個 envelope 欄位等於 expected artifact -> CONFIG_INVALID
6. 解析 rows 並驗證 dataset_id 與 as_of_date -> DATA_QUALITY
```

metadata 只載入一次、raw bytes 只讀一次，`normalize()` 不呼叫 `fetch()`，避免同一次 normalize 內重複 I/O 與 TOCTOU 漂移。

## 六、共享 helper 重構（checklist 6）

新增三組模組層級的純函式，`fetch()` 與 `normalize()` 共用同一套「什麼才算正確」的定義：

| helper | 職責 | 純度 |
| --- | --- | --- |
| `_build_expected_request(metadata, file_name)` | 由 metadata 建出唯一 expected `FetchRequest` | 不讀檔、不讀時間、不產生 UUID |
| `_build_expected_artifact(entry, request, content_hash, raw_file_name)` | 由 envelope、expected request 與 raw hash 建出 expected `RawArtifact` | 同上 |
| `_mismatched_request_fields` 與 `_mismatched_lineage_fields` | 回傳不相符的欄位**名稱**，不回傳值 | 同上 |

`fetch()` 現在是：載入 metadata、查 envelope、建 expected request、比對呼叫端 request、讀 raw bytes、交給 `_build_expected_artifact`。`normalize()` 用同兩個 helper 算出「這次應該產生什麼」再比對。兩者不會再對正確性有各自的定義。

I/O 次數：`normalize()` 內 metadata 載入 1 次、raw bytes 讀 1 次，不呼叫 `fetch()`。

## 十二、healthcheck 失敗語意（checklist 13）

### 12.1 三種情境

| 情境 | 行為 | ErrorCode |
| --- | --- | --- |
| metadata 檔案不存在 | 拋錯 | `SOURCE_PERMANENT` |
| metadata 存在但不合契約（含無法解析的 JSON） | 拋錯 | `DATA_QUALITY` |
| metadata 識別與 adapter 不符 | 拋錯 | `CONFIG_INVALID` |
| metadata 可信但 raw 檔案缺少 | 回傳 `SourceHealth(healthy=False)`，`checked_at` 仍為固定值 | 不適用 |

判準只有一條：**能不能取得可信的固定 `checked_at`**。能，就回傳健康快照；不能，就拋結構化錯誤。不注入任何 fallback time。
