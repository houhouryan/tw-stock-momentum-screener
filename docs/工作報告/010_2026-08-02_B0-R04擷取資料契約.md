## 五、問題、偏差與風險

### V-1　`http_status` 需採 strict 模式（實作調整，非規格偏離）

見 §四 4.1。Pydantic 預設會把 `"200"` 強制轉成整數，與 §10.3「非 integer 拒絕」牴觸。修正方式是為該欄位加 `strict=True`，仍在授權檔 `acquisition.py` 內，**未改變 §9.3 定義的欄位型別或語意**。

我**只對 `http_status` 加 strict**，未擴及 `retry_count`、`row_index` 等其他整數欄位——檢查報告只對 `http_status` 明文要求，我不自行擴張。這一點列為觀察供審查者裁示是否需要一致化。

### V-2　`rows` 的公開型別為 `list`，非 §9.5 字面的 tuple

§9.5 寫 `rows` 為「tuple of JSON objects」。我的實作**內部以不可變 JSON 字串保存**，公開 property 每次回傳新的 `list`。

理由：§9.1 要求「直接嘗試修改公開 JSON mapping／sequence 的根層或巢狀值，也必須被拒絕，**或只作用於不會回寫模型的 fresh copy**」。tuple 只能防止根層 rebind，**無法防止巢狀 dict 被 mutate**；JSON snapshot 才能同時滿足巢狀防污染與 JSON 序列化。

`normalization_errors` 則維持 `tuple[NormalizationIssue, ...]`，因其元素本身即 frozen model，不需 snapshot。

若審查者認為 `rows` 公開型別必須字面為 tuple，我可在下一輪調整為回傳 tuple；**本輪不自行更動已核准的行為要求**。

### V-3　`FetchRequest` 等有一個 `exclude=True` 的內部欄位

為實作 snapshot 策略，四處 JSON 欄位各有一個 `*_snapshot: str` 內部欄位（`repr=False, exclude=True`）。它不出現在 `model_dump()`，公開介面由 property 提供，且 `model_dump()` 已覆寫為輸出解碼後的 JSON 值。

`acquisition.py` 的 `__all__` **只列五個 model**，未把 private validator、secret fragments 或 `JsonValue` 當穩定 API（§9.7）。
