## 三、修復內容

### 3.1 真實公開欄位（F01）

移除三種 `*_snapshot` Pydantic field，以及為它們存在的**四個 custom `__init__`** 與**四個 custom `model_dump`**。未改用 alias、computed field、serializer alias 或其他可由 constructor 傳入的 hidden field。

真實欄位直接命名：

```python
request_json: JsonObject = Field(default_factory=dict)
evidence: JsonObject = Field(default_factory=dict)
rows: tuple[JsonObject, ...] = ()
```

### 3.2 三層 JSON 策略（F02）

| 層 | 作法 |
|---|---|
| **建構時** | `mode="before"` field validator 遞迴重建 canonical 結構：逐層依 key 排序、拒絕非 JSON 型別與疑似密鑰、**不保留呼叫端任何 reference** |
| **讀取時** | 基底類別 `_AcquisitionModel.__getattribute__` 對 `_json_guarded_fields`（`ClassVar[frozenset[str]]`）列出的欄位回傳 `copy.deepcopy` |
| **序列化時** | Pydantic 序列化器直接讀 `__dict__`，不經過 `__getattribute__`，因此**無須覆寫任何 dump 方法** |

`_canonical_json_value()` 的精確規則：允許 null／str／bool／int／有限 float／list／dict；**bool 在 int 之前判斷**（Python `bool` 是 `int` 子類別）；container 用 `type(...) is` 精確比對，因此 tuple、set、bytes、自訂 Mapping 與任意物件全部拒絕，不交給 `json.dumps()` 靜默轉換。

### 3.3 rows 契約（F03）

- public annotation 與 runtime 皆為 `tuple[JsonObject, ...]`。
- `_canonical_rows()` **只對最外層** container 接受 list 或 tuple（JSON round-trip 會把 outer array 解成 list，必須能接受），每個 row 內部仍只接受 list，**巢狀 tuple 一律拒絕**。
- `row_count` 依 `self.__dict__["rows"]` 的 canonical 儲存值驗證。
- empty rows ＋ issues 與 Raw 解耦行為保留。

### 3.4 canonical equality（F03）

每層 object 依 key 排序後重建，因此相同語意但不同插入順序的輸入會產生**相同的 dict 與相同的序列化文字**，model equality、`model_dump(mode="json")` 與 `model_dump_json()` 三者皆一致。

### 3.5 strict scalar（§6.7）

| 欄位 | 作法 |
|---|---|
| `http_status` | `Field(strict=True)` |
| `retry_count`、`row_count` | `NonNegativeInt = Annotated[int, Field(ge=0, strict=True)]` |
| `row_index` | `Field(strict=True)` + 非負檢查 |
| `healthy` | `Field(strict=True)`，拒絕 `"true"`／`"false"`／0／1 |
| non-empty str | `NonEmptyStr = Annotated[str, Field(min_length=1, strict=True)]` |
| `UUID`、`AwareDatetime` | **維持非 strict**，保留標準 JSON round-trip 能力 |

### 3.6 §6.8 保持不變

五個 class 名稱與 `__all__`、RawArtifact 十欄位與 hash 語意、時區／license／retry／normalize 解耦、`domain/__init__.py` export、無 I/O／網路／now／random default、未修改 errors——**全部維持**。

## 六、問題、偏差與風險

### V-1　我的原始設計是錯的，且是安全缺陷

`*_snapshot` 是**真正的 Pydantic field**，不是私有實作。我誤以為 `exclude=True` 能讓它變成內部欄位，實際上它只影響 dump，**不影響 schema、signature 或 constructor**。結果是密鑰驗證可被公開 constructor 完全繞過。

這不是風格問題。若 Adapter 依此契約實作，`api_token` 這類值可能被寫進結構化 log 或 artifact metadata。**審查者的負向探針抓到了我的測試完全沒覆蓋的公開 API 邊界。**

我的 109 個測試全綠卻沒守住介面，因為它們只驗證 `model_dump(mode="json")`，沒有驗證 `model_fields`、`model_json_schema()`、`inspect.signature()`、`model_dump_json()` 與舊欄位名稱是否可繞過。**測試覆蓋率不等於契約覆蓋率。**

### V-2　`__getattribute__` 與 Pydantic 序列化器的分工

fresh-copy 由基底類別的 `__getattribute__` 提供，而 Pydantic v2 的序列化器直接讀 `__dict__`（Rust core），不經過該方法。因此：

- 呼叫端 `model.request_json` 取得 deep copy，無法回頭污染。
- `model_dump()`／`model_dump_json()` 看到已驗證的儲存值，資料完整。

兩者不衝突，也因此**不需覆寫任何 dump 方法**——這正是審查者 §6.4 推薦且已驗證的策略。

### V-3　lint 兩次小失誤（已修正）

`RUF002` 全形分號與 `F401` 多餘 import，見 §5.3。前者是我第三次在新 docstring 誤用非白名單全形字元（前兩次為 `；／` 與 `～`）。**往後撰寫 docstring 只使用 `，：（）` 與非 confusable 的 `。`、`、`。**
