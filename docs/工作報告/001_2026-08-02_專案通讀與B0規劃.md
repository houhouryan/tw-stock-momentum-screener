## 三、發現的問題

四項，均已寫入 README 與 B0 計畫 §8.2，此處摘要。

### F-01　分工在最新 commit 被對調（嚴重度：高）

| 文件 | 組員 A | 組員 B |
|---|---|---|
| 計畫書 v2.6.1 §17 | 資料與**系統工程**（含新聞爬蟲） | 研究、消息與評估 |
| 最新工作表（commit `9db0e8c`） | 市場資料與**研究** | **系統**、實驗與模型 |

**兩份文件互相矛盾且方向相反。** 依 SDD 文件優先序應以較新的工作表為準，但計畫書 §17 未作廢，任何人讀到都會拿反。**建議發 ADR 正式作廢計畫書 §17。**

實務影響：既有 `src/` 新聞擷取器是在舊分工下由「A」寫的，現在落在 B 的職責範圍。

### F-02　新聞擷取器 PIT schema 不符雙 PIT 要求（嚴重度：中）

`src/db.py` 與 `src/sources.py`：

| 項目 | 現況 | SDD §7.1–7.2 / 計畫書 §8.5.4 要求 |
|---|---|---|
| PIT 時間 | 單一 `available_from = max(published_at, fetched_at)` | **分開保存** `system_available_from`(=first_seen_at) 與 `public_available_from`(=published_at)，不得互相覆蓋（DD-013） |
| 發布時間 | 只存解析後的 `published_at` | `published_at_raw`（頁面原樣，**不解析**）＋ `published_at_parsed`（可為 null） |
| run 關聯 | `news_raw` 無欄位指向 `crawl_run` | 需 `retrieved_run_id` |
| 內容 | 只有 `summary` | 需 `body` 與 `raw_html` |
| `content_hash` | 標題＋摘要的 hash（偵測改稿） | SDD 定義為**原始 bytes** 的 SHA-256（語意衝突，需改名區分） |

**重要判斷：取 `max()` 的方向是保守的**——它延後資料可用時間，不會讓決策層提早看到資料，**因此不構成 leakage**。問題在欄位形狀不符雙 PIT 要求，而非資料正確性。

### F-03　SDD 依據的計畫書版本缺漏（嚴重度：中）

SDD §1 表頭宣稱「主要依據：專案計畫書 **v2.6.2**」，但 repo 內只有 **v2.6.1**。引用計畫書條號時無法確認該條是否已在 v2.6.2 被修改。**建議補入 v2.6.2，或明確宣告以 v2.6.1 為準。**

### F-04　systemd 有未寫明的隱藏死線（嚴重度：中）

SD-AC07 要求「連續 10 個交易日無人工介入完成 acquisition、manifest、score、scorecard、backup」，SDD 註明「預計最早於 12/3 達成」。

從 12/3 倒推 10 個交易日 ≈ **2026-11-19**。

但組員 B 工作表把 systemd 放在 B5-04，B5 階段從 11/5 才開始，且 systemd 是該階段九項中的第四項。**照順序做會來不及。建議把 systemd 提前到 B4 期間先產出可運行版本，B5 只做強化與故障演練。**
