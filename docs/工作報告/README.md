# 工作報告

本資料夾存放組員 B 每一輪工作的**規劃與執行報告**。

**本規範為生效中的正式規則，非草案。**

---

## 一、不可變更規則

依 [ADR-0001 DEC-012](../adr/ADR-0001-B0基線決策.md)：

| 規則 | 說明 |
|---|---|
| **不可覆寫** | 既有工作報告的內容不得修改。發現錯誤時新增後續報告更正，不回頭改舊報告 |
| **不可改名** | 檔名一經建立即固定，包含流水號與日期 |
| **不可刪除** | 任何情況下都不刪除既有報告，包含失敗、退回或作廢的輪次 |

**理由：** 報告是審查者與工程師之間的唯一非同步溝通來源。允許覆寫會使規劃可被事後回溯修改，失去稽核價值。

唯一例外：**當輪報告在該輪執行期間可持續補寫**（規劃 → 執行結果 → 收尾）。一旦該輪結束並送審，即凍結。

---

## 二、一輪一停

依檢查報告 §5.1：

1. 只執行**目前被解鎖**的輪次
2. 勾選該輪 checklist 並保存驗證輸出
3. 在本資料夾新增一份工作報告
4. **停止工作，不開始下一輪**
5. 等待 `docs/reviews/member-b/` 中新的檢查報告
6. 只有檢查結論為 **PASS**，且明確寫出下一輪 ID，才能繼續

> **即使本輪提早完成，也不得順手建立下一輪檔案。**

### 遇到決策或阻塞

- 立即停止，**不自行採用預設方案**
- 報告狀態標為 `BLOCKED`
- 說明背景、選項、影響與建議
- 不開始下一輪

---

## 三、Checklist 使用方式

- **不修改檢查報告本身**
- 將當輪 checklist **原樣複製**到工作報告，再以 `[x]`／`[ ]` 標記
- 未完成項目**保留 `[ ]` 並解釋原因**，不得刪除
- 額外完成的工作列為**範圍外變更**；範圍外變更可能導致整輪退回

---

## 四、工作流程

**不得先動手再補規劃。**

```
1. 規劃    →  2. 確認    →  3. 執行      →  4. 收尾
   寫步驟       送審核准      照步驟逐項做     補完報告
```

| 步驟 | 動作 | 產出 |
|---|---|---|
| **1. 規劃** | 建立本輪報告檔，**先只寫「本輪規劃步驟」** | 報告檔（規劃版） |
| **2. 確認** | 送交確認。**未確認前不得執行任何步驟** | 核准 |
| **3. 執行** | 依編號逐步執行，每完成一步即更新狀態 | 程式、設定、測試 |
| **4. 收尾** | 補完其餘章節，特別是「問題、偏差與風險」 | 報告檔（完整版） |

規劃先寫進檔案再執行，目的是**讓規劃無法事後回溯修改**。若執行中發現規劃有誤，不得偷改規劃，須據實記錄偏差。

---

## 五、命名規則

```
NNN_YYYY-MM-DD_主題.md
```

- `NNN`：三位數流水號，依執行順序遞增
- `YYYY-MM-DD`：該輪工作日期
- 主題含輪次 ID，例如 `B0-R00決策與文件基線`

範例：`002_2026-08-02_B0-R00決策與文件基線.md`

## 六、報告格式

依檢查報告 §21，固定八節。**報告必須自足**——審查者不需詢問即可完整理解與重現。

### 表頭

| 欄位 | 說明 |
|---|---|
| 日期／耗時 | 實際耗時，非預估 |
| 狀態 | `COMPLETE` / `INCOMPLETE` / `BLOCKED` |
| Branch | 執行時所在分支 |
| **Base commit** | 本輪開始時的 commit hash |
| **Head commit** | 結束時的 commit hash；尚未提交就明寫 `uncommitted` |
| 對應檢查報告 | `docs/reviews/member-b/...` 的路徑與章節 |

### 八節

| # | 章節 | 內容 | 何時寫 |
|---:|---|---|---|
| **一** | **Checklist** | 原樣複製當輪 checklist，`[x]`／`[ ]` 標記；未完成須說明原因 | 執行中 |
| 二 | 本輪變更 | 列出檔案、symbol、目的；**區分「本輪修改」「本輪前已存在」「他人同時修改」** | 執行中 |
| 三 | 驗證證據 | 完整命令、exit code、關鍵輸出。**沒有執行就明寫未驗證** | 執行中 |
| 四 | Git 證據 | `git status --short`、`git diff --stat`、commit stat 或未提交原因 | 收尾 |
| 五 | 問題、偏差與風險 | 失敗測試、範圍外變更、與指引不同之處、工時高低估 | 收尾 |
| 六 | 待決事項 | 沒有就寫「無」。有則立即停止，不自行選擇 | 收尾 |
| 七 | 給審查者的重現步驟 | 從 repo 當前狀態開始，**逐條可執行** | 收尾 |
| 八 | 停止聲明 | 明寫下一輪 ID 尚未開始，等待檢查報告 | 收尾 |

> **「本輪規劃步驟」置於第一節之前或併入第一節**，於執行前寫定。

---

## 七、「本輪規劃步驟」的規格

**要非常詳細。** 每個步驟必須是可獨立驗證的最小單位——若一個步驟無法用一句話說明「怎麼知道它做完了」，代表切得太粗，要再拆。

每步驟必含七欄：

| 欄 | 說明 |
|---|---|
| `#` | 步驟編號，依執行順序 |
| 動作 | 具體做什麼。**禁止「實作 XXX 模組」這種粒度** |
| 產出檔案 | 完整路徑，標明新增或修改 |
| 完成判準 | 怎麼知道這步做完了，須可客觀驗證 |
| 驗證方式 | 實際要跑的指令或檢查動作 |
| 依賴 | 依賴前面哪幾個步驟編號；無則填「—」 |
| 預估 | 分鐘或小時 |

步驟表後另需標明：

- **決策點**：哪些步驟執行前需要先問，問什麼
- **風險步驟**：哪幾步最可能失敗或超時，失敗時的退路
- **本輪明確不做**：排除的項目，避免範圍蔓延

## 八、Git 證據要求

依檢查報告 B0-F07，每份報告必附：

```bash
git branch --show-current
git rev-parse HEAD          # 開始時記錄為 base，結束時記錄為 head
git status --short
git diff --stat             # 或本輪 commit 的 stat
```

並明確區分：

- **本輪修改**——這一輪動的
- **本輪前已存在**——進入本輪時就在的未提交變更
- **他人同時修改**——執行期間出現的他人變更

目的是讓審查者**不需猜測**，即可把報告中的交付物對應到確切 diff。

## 九、寫作原則

1. **失敗與未完成要寫進去。** 測試沒過就貼輸出，步驟跳過就說跳過。報告不是成果展示。
2. **不重複貼程式碼。** 指出檔案路徑與行號即可。
3. **待決事項一定附建議**，不丟開放式問題。
4. **與規劃有出入一定要寫**，包含工時高估或低估。
5. **規劃寫定後不得回頭修改**，差異一律記在第五節。
6. **不得使用「未反對視為同意」。** 沉默不是核准。

## 十、完成標記

工作報告與檢查報告**雙向**都必須在檔案最後一行加註完成標記，作為「已寫完、可以開始讀」的零歧義訊號。

| 文件 | 標記 | 寫入者 |
|---|---|---|
| 組員 B 工作報告 | `<!-- REPORT-COMPLETE -->` | 組員 B |
| 檢查報告 | `<!-- REVIEW-COMPLETE -->` | 審查者／專案經理 |

### 規則

1. **標記代表整份文件已完成**，出現後不再續寫。
2. **只在收尾階段寫入**，規劃版與執行中的報告**不得**先放標記。
3. 標記必須是**檔案最後一行**，前面不接其他內容。
4. **沒有標記 = 尚未寫完。** 對方會持續等待，不會提前讀取。
5. 標記寫入後即凍結；發現錯誤時新增後續報告更正，不回頭改。

### 為什麼需要

雙方以非同步方式協作：組員 B 完成一輪後進入等待，偵測到帶有 `REVIEW-COMPLETE` 的新檢查報告才恢復工作。若無標記，就必須靠檔案修改時間等啟發式判斷，可能在報告寫到一半時誤判並據以開工。
